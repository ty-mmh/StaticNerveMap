# StaticNerveMap

## 目的
本プロジェクトは、既存のソースコードを静的解析し、クラス、メソッド、依存関係、呼び出し関係などを神経系のように俯瞰できる基盤情報を構築することを目的とする。

最終的には、何を変更すると何に影響し、どのような破壊や不整合が起こり得るかを分析できる形で、解析結果を `yaml` として出力する仕組みを検討する。

## 利用者
本プロジェクトの主な利用者は、既存ソースコードを保守・改造する開発者、および Codex や Claude Code といった AI エージェントである。

特に、静的解析結果の基盤情報 `yaml` は、AI エージェントによるソースコード改造時の文脈入力として利用することを目的とする。

## 出力
出力の中心は、ソースコード解析結果を正規化した基盤情報 `yaml` とする。

この `yaml` には、少なくとも次のような情報を載せられる状態を目指す。

- クラス、メソッド、関数、モジュールなどの構成要素
- 呼び出し関係、参照関係、依存関係
- 継承、実装、所属などの構造的関係
- 変更時の影響範囲をたどるための関連情報
- AI エージェントが安全に改造判断するための補助情報

## 解析方針
本プロジェクトで行う静的解析は、LLM や MCP に依存しない走査ベースの解析を前提とする。

つまり、解析そのものは構文解析、シンボル抽出、参照解決、依存追跡などの静的処理で成立させる。

一方で、解析結果として生成される `yaml` は、後段で AI エージェントが読むことを想定した出力とする。

## 非目的
現時点では、次のものは本プロジェクトの主目的に含めない。

- LLM を用いた解析そのもの
- MCP サーバーの提供そのもの
- 対話 UI やチャット UI の構築そのもの
- 解析結果の主保存先をグラフ DB にすること

## GitNexus から流用を検討する点
GitNexus は、既存コードを解析して依存関係、呼び出し連鎖、実行フロー、影響範囲を扱う先行例として参考になる。

本プロジェクトでは、特に次の観点を流用候補として検討する。

- Tree-sitter などを用いた静的解析の考え方
- クラス、メソッド、依存、呼び出しをグラフ的に表現する内部モデル
- 変更影響範囲をたどるための関係抽出の考え方
- AI エージェントが利用しやすい文脈情報の粒度設計

## GitNexus からそのまま流用しない点
GitNexus は MCP や AI エージェント連携を主眼に置いたツールであり、本プロジェクトとは成果物の形が異なる。

そのため、次の点はそのまま採用しない前提で検討する。

- MCP を中心にした提供形態
- 対話ツールとしての `query` や `impact` を直接の成果物とする設計
- グラフ DB を前提にした利用形態
- Web UI を中心にした探索体験

## 現時点の基本方針
StaticNerveMap は、GitNexus のようなコード構造把握の考え方を参考にしつつも、目的を AI エージェント向けの静的解析基盤 `yaml` 出力に絞ったプロジェクトとして整理する。

## 現在状態との整合
現時点の実装は、当初の目的と大きくはずれていない。

すでに次の要素は、Python 限定ではあるが実装済みである。

- `yaml` 出力を中心にした静的解析パイプライン
- file / symbol / import / call / inherits の抽出
- `entrypoints`、`change_targets`、`clusters`、`api_contracts`、`unresolved`
- AI エージェントの改造初動を支えるための `ui_binds`、route / command bind、impact の足場情報
- 低信号な未解決 call を抑制しつつ、不確実な箇所を `severity` 付きで残す仕組み

特に、出力が「コード理解の一般論」ではなく、AI エージェントが

- どこから読むべきか
- どこを先に触るべきか
- どこが未解決で再確認が必要か

を判断するための足場になっている点は、当初の目的と整合している。

一方で、まだ未完の点もある。

- 現状の主対象は Python であり、多言語解析には未対応
- `yaml` は改造初動にかなり有用になってきたが、変更影響の深い推論は今後の拡張余地がある
- `pyproject.toml` / `requirements.txt` の依存読み取りや、より高度な型伝播は今後の候補である
